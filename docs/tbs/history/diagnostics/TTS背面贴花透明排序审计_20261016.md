# TTS 背面底栏与数字的透明排序审计

2026-10-16。只读检查安装目录的 Assembly-CSharp.dll 与 resources.assets；没有修改游戏文件、Global 或素材。

## 已证实的引擎行为

1. `DecalManager.CreateDecal(DecalState, NetworkView, UInt32)` 对每张贴花都实例化 `Resources.Load("Decal")`，直接应用 localPosition、localEulerAngles、localScale。
2. 资源中的 Decal GameObject path_id 为 8352，使用 MeshRenderer；其 sortingLayerID / sortingOrder 均为 0。
3. 该 Renderer 的 Decal 材质使用 `Marmoset/Transparent/Diffuse IBL` shader。SubShader 的 `QUEUE=Transparent`、`RenderType=Transparent`。
4. shader 两个 pass 都是 `zWrite=0`，即不写深度。第一个 pass 使用 SrcAlpha(5) / OneMinusSrcAlpha(10)，zTest 为 LessEqual(4)。因此贴花虽可与棋面正确通过深度测试，彼此之间仍依赖透明绘制顺序。
5. 材质保存属性中的 `_ZWrite=1` 是遗留属性，不能代表当前 shader 的实际行为；应以上述 pass state 为准。
6. `LoadingImageFinished` 仅给第一份匹配 Renderer 的材质设置 mainTexture，其余同 URL 贴花复用 sharedMaterial。整个 DecalManager 未设置 renderer.sortingOrder 或 material.renderQueue。

## 对最新截图的解释

背面大底栏与数字、行动图标具有不同中心点。在两边相反的斜视角，消失的是不同一端的数字和图标。这与透明对象按相机距离排序、底栏后绘制并盖住其中部分贴花的机制高度吻合。不能再把它等同于两层距离过近的 z-fighting；单纯增加垂直间距不能保证任意视角都正确。

把底栏直接合入棋子背面纹理，再删掉独立底栏贴花，可消除这一组叠加透明 Renderer 的竞争。数字、未／済仍可保留独立可替换贴花。

## API 范围

`LuaObject.SetDecals` 只消费 name/url/position/rotation/scale，不能直接指定贴花排序。官方 Component API 确有进一步操纵 MeshRenderer 的路线：`LuaComponentReference.set` 转交 `LuaObject.setComponentVar`，后者允许标准非 MonoBehaviour 组件的白名单字段类型并具备 Int32 同步分支。但本次不采用此路线。

原因：Decal GameObject 并没有获得 Lua decal.name；所有实例可能同名，可靠定位需要额外几何匹配。每次 setDecals 都会销毁重建贴花，也需重新绑定排序。另需验证客户端同步与保存加载的边界，不能只凭属性存在就承诺可靠。
